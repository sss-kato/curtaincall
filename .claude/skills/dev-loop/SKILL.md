# dev-loop — 実装・レビュー・修正のループ

あなたはこのループの**司令塔**です。自分ではコードを書かず、レビューもしません。エージェントを呼び、結果を判定し、指摘を統合して次のエージェントに渡します。

## 入力

`$ARGUMENTS` にタスクが入る。以下のいずれか。

- **タスク ID（通常）**：例 `T-05`。`docs/tasks/T-05.md` を読み、「内容」「完了条件」「参照」を取得する。frontmatter の `stack` が対象スタック
- 機能 ID（例：`F-01`）→ `docs/requirements.md` の該当行を読む
- 自由記述（例：「宝塚の Source を実装」）
- 指摘 ID（例：「前回の残課題 M-3 M-7 を対応」）

タスク ID で起動した場合の追加チェック：
- タスクファイルの `status` が `in_progress` であること。`todo` なら「pm dispatch されていません」、`review` / `done` なら「すでに完了しています」と停止
- 現在のブランチが frontmatter の `branch` と一致すること。違えば停止して worktree の場所を伝える

タスクが曖昧で、対象が `app/` か `collector/` か判断できない場合のみ開発者に確認する。それ以外は確認せず開始する。

## 事前準備

1. `CLAUDE.md` を読む（規約・エージェント一覧・ループ定義）
2. タスクから対象スタックを決める：`app` / `collector` / `both`
3. `git status` で作業ツリーが clean か確認する。未コミットの変更があれば開発者に確認する（ループ中の差分と混ざるため）。タスク ID 起動時は `docs/tasks/T-xx.md` 以外の変更がないこと
4. 開始時の commit を記録する：`BASE=$(git rev-parse HEAD)`。以降のレビューは `git diff $BASE` を対象にする

## ループ本体

### Step 1. 実装

対象スタックの実装エージェントを Agent ツールで呼ぶ。`both` なら `collector-dev` → `flutter-dev` の順（データ形式が先に決まる）。

依頼に含めるもの：
- タスクの内容（機能 ID なら要件書の該当行を引用）
- 「新規実装」であること
- 完了報告フォーマットで返すこと

実装報告の `品質ゲート` が NG なら、同じエージェントに「品質ゲートを通してから報告すること」と差し戻す（これはループ回数に数えない。最大2回）。

### Step 2. 第1段階レビュー（並列）

以下を**1つのメッセージで同時に**呼ぶ。全員に同じ依頼文を渡す。

| 対象 | 呼ぶレビュアー |
|---|---|
| app | spec / architecture / adversarial / security / **flutter-expert** |
| collector | spec / architecture / adversarial / security / **typescript-expert** |
| both | 上記6人すべて |

依頼文のテンプレート：

```
レビュー対象: git diff <BASE> -- <app/ または collector/ または両方>
タスク: <タスクの内容>
完了条件: <タスクファイルの「完了条件」を転記。spec-reviewer はこれを判定に使う>
第 <N> 周目（前回の指摘: <あれば統合済み指摘の一覧、初回は「なし」>）
出力フォーマットに従って返してください。
```

**注意**：ループ中はコミットしないため、diff は `git diff <BASE>`（作業ツリーとの比較）で取る。

### Step 3. 判定と統合

全員の結果を受け取り、`判定:` 行を集計する。

- **全員 PASS** → Step 5 へ
- **1人でも FAIL** → 指摘を統合して Step 4 へ

#### 指摘の統合ルール

1. 全レビュアーの指摘を「場所（ファイル:行）」で並べる
2. **同じファイルで行番号が ±5 以内、かつ同じ問題を指す**ものは1件にまとめる。迷ったらまとめない
3. まとめた指摘の重大度は**最も高いもの**を採る
4. 通し番号 `[M-1]` `[M-2]` … を振り直す（M = merged。レビュアーの `[R-n]` と区別）
5. **各レビュアーの根拠・修正案は削らずすべて残す**
6. 重大度「低」のみの指摘は修正依頼に含めない（第2段階または最終報告で列挙する）

統合後のフォーマット：

```
#### [M-1] <重大|高|中> <一行要約>
- 場所: collector/src/infrastructure/sources/toho.ts:42
- 指摘元: architecture / security / typescript-expert
- 根拠（architecture）: CLAUDE.md「高凝集・疎結合」— sources から fetch を直接呼んでいる
- 根拠（security）: 要件 §5 — タイムアウト・UA がない
- 根拠（typescript-expert）: Node fetch — response.ok 未確認
- 修正案: infrastructure/http の fetchWithPolicy() 経由にする。ラッパー側で UA・タイムアウト・ok 確認を行う
```

### Step 4. 修正

実装エージェントに統合済み指摘を渡す。

依頼に含めるもの：
- 「レビュー指摘の修正」であること
- 統合済み指摘の全文
- 「対応しなかった指摘には理由を書くこと」
- 完了報告フォーマットで返すこと

実装報告に「対応しなかった指摘」があれば、その理由を記録しておく（次のレビュー依頼と最終報告に含める）。

周回カウントを +1 し、**3周に達していなければ Step 2 へ**。達していれば Step 7（打ち切り）へ。

### Step 5. 第2段階レビュー（並列）

`readability-reviewer` と `maintainability-reviewer` を同時に呼ぶ。依頼文は Step 2 と同じテンプレート。

- **両方 PASS** → Step 6 へ
- **FAIL** → Step 3 と同じルールで統合し、Step 4 と同じ手順で修正。修正後は **Step 5 に戻る**（第1段階には戻らない）。第2段階も3周で打ち切り

### Step 6. 検証

`verifier` を呼ぶ。対象スタックを伝える。

- **PASS** → Step 8（完了報告）へ
- **FAIL** → 実装エージェントに検証結果を渡して修正させ、再度 verifier（最大2回。これもループ回数に数えない）

### Step 7. 打ち切り

3周で収束しなかった場合。以下を含めて開発者に報告し、**判断を仰いで停止する**。

- 最後の周で残っていた指摘（統合済み）
- 各周で何が直り、何が残ったかの推移
- 実装エージェントが「対応しなかった」と申告した指摘とその理由
- 推奨する次の一手（規約を変えるべきか、設計を見直すべきか、指摘が過剰か）

タスク ID 起動時は、タスクファイルの「dev-loop 結果」に打ち切り報告を追記する。`status` は `in_progress` のまま（再開は `/dev-loop T-xx 前回の M-n を対応` で行う）。

### Step 8. 完了報告

#### 8-1. タスクファイルへの記録（タスク ID 起動時のみ）

`docs/tasks/T-xx.md` を更新する。

- frontmatter の `status` を `review` にする
- 「完了条件」のチェックボックスを、spec-reviewer の最終結果に基づいて埋める
- 「dev-loop 結果」セクションに、下記 8-2 の報告本文をそのまま追記する

これはループ中で唯一のファイル編集であり、コミットはしない（`pm pr` が行う）。

#### 8-2. 開発者への報告

以下のフォーマットで報告する。

```
## dev-loop 完了

タスク: T-xx <タイトル>
対象: app / collector / both
周回: 第1段階 N 周 / 第2段階 N 周
検証: PASS

### 変更ファイル
- <実装報告から転記>

### 修正した指摘の要約
| 周 | 件数 | 主な内容 |
|---|---|---|
| 1-1 | 5 | ... |
| 1-2 | 1 | ... |
| 2-1 | 2 | ... |

### 残っている「低」の指摘
- [M-n] <内容>（対応は任意）

### 対応しなかった指摘
- [M-n] <理由>（なければ「なし」）

### 開発者に確認してほしいこと
- <設計判断・要件の解釈で実装エージェントが仮定を置いた点。なければ「なし」>

次のステップ:
1. この worktree で最終レビューと動作確認
2. 問題なければ `/pm pr T-xx`
```

## 禁止事項

- 司令塔がコードを直接編集すること（必ず実装エージェント経由）
- レビュアーの指摘を司令塔の判断で却下すること（却下は実装エージェントが理由付きで行い、開発者が最終判断する）
- 周回上限を超えて続けること
- コミットすること（ループはコミットしない。`pm pr` が開発者の確認後に行う）
- `docs/tasks/T-xx.md` 以外のファイルを司令塔が編集すること

## 実行例

```
/dev-loop T-05                                  # 通常。pm が払い出した worktree で
/dev-loop T-05 前回の打ち切り報告の M-2 M-4 を対応   # 打ち切り後の再開
/dev-loop 宝塚の日付パースを JST に修正             # ボード外の小さな修正
```
