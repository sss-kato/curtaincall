## 1. 概要

### 1.1 一言でいうと

**舞台・ミュージカルの公式情報を一箇所に集約する、iOS 向けニュースアグリゲーター。**

### 1.2 背景と課題

宝塚歌劇団・劇団四季をはじめとする複数の劇団・製作会社の情報を追うには、それぞれの公式サイトを個別に巡回する必要がある。新作発表やチケット発売日の告知は各社バラバラのタイミングで出るため、以下の問題が生じている。

- 複数サイトを毎日横断する手間がかかる
- チケットの発売日・抽選申込の締切を見逃すリスクがある
- どこで何が発表されたかを一覧で把握できない

### 1.3 解決する姿

アプリを開けば、対象5団体の最新情報が**時系列で一覧表示**される。新着があれば**プッシュ通知**で知らせる。詳細は公式サイトへ遷移して読む。

UI の参考イメージは **SmartNews**（上部に団体タブ、横スワイプで切り替え）。

## 3. スコープ

### 3.1 対象団体（5団体）

| # | 団体名 | 備考 |
|---|---|---|
| 1 | 宝塚歌劇団 | 花・月・雪・星・宙の各組 |
| 2 | 劇団四季 | |
| 3 | ホリプロステージ | |
| 4 | 東宝（演劇） | 帝国劇場ほか |
| 5 | 劇団☆新感線 | |

将来的に団体を追加できるよう、**団体の定義は設定ファイル（JSON）で外出し**し、アプリ本体の改修なしに増やせる構造とする。

### 3.2 情報源

**各団体の公式サイトのみ。**

Phase 0 の調査により、以下の取得方法が確定した（詳細は[調査レポート](./research/site-survey.md)）。

| 団体 | 取得元 | 方式 |
|---|---|---|
| 宝塚歌劇団 | `kageki.hankyu.co.jp/news/` | HTML 解析 |
| 劇団四季 | `www.shiki.jp/navi/news/` | HTML 解析 |
| ホリプロステージ | `horipro-stage.jp/feed/` | **RSS** |
| 東宝 | `www.toho.co.jp/stage/topics/` ほか | HTML 解析 |
| 劇団☆新感線 | `blog.vi-shinkansen.co.jp/?feed=rss2` | **RSS** |

**全サイトが静的 HTML を返すため、ヘッドレスブラウザは不要。** また、robots.txt で自動取得を制限しているサイトは1件も無かった。

以下は対象外とする。

| 対象外 | 理由 |
|---|---|
| チケット販売サイト（ぴあ、イープラス等） | 利用規約で自動取得を禁止しているケースが多く、ログインが必要な画面も多い |
| 公式 SNS（X／Twitter） | API が有料化され、個人開発の無料枠では実質利用できない |
| 演劇ニュースメディア（ステージナタリー等） | 公式情報との重複が発生するため、MVP では見送り |

### 3.3 収集する情報カテゴリ

**優先度高（★）が通知およびカテゴリ分類の中心。**

| 優先 | カテゴリ | 内容 |
|---|---|---|
| ★1 | 新作発表 | 上演決定のお知らせ |
| ★2 | チケット情報 | 発売日告知（先行・一般）、**抽選の申込期間・当落発表日** |
| ★3 | 配信・映像化 | DVD 発売、配信サービスでの公開 |
| | 公演スケジュール | 日程・劇場 |
| | キャスト情報 | 配役発表 |
| | 出演者ニュース | 退団・移籍・受賞など |
| | 当日券・立ち見 | ※取得可能な範囲のみ（後述のリスク参照） |
| | 残席状況 | ※同上 |

### 3.4 明確にスコープ外とするもの

- 公演の中止・変更・代役情報（優先度低として今回は対象外）
- グッズ・関連商品情報
- チケットの購入機能（公式サイトへのリンクのみ提供）
- 記事本文のアプリ内表示（権利面の配慮。見出しとリンクのみ扱う）
- Android 版（Flutter 採用により将来的に可能だが、当面は対象外）

## 4. 機能要件

### 4.1 MVP に含める機能

| ID | 機能 | 内容 |
|---|---|---|
| F-01 | **記事一覧表示** | 上部に団体タブ（すべて／宝塚／四季／ホリプロ／東宝／新感線）。横スワイプで切替。新着順に表示 |
| F-02 | **記事項目の表示** | 団体名・カテゴリアイコン・見出し・公開日・（取得できれば）サムネイル。時刻は表示しない（HTML 解析の 3 団体は掲載日のみで時刻を持たないため。S-00 §8 #15） |
| F-03 | **記事を開く** | タップでアプリ内ブラウザ（SFSafariViewController）が起動し公式ページを表示 |
| F-04 | **ブラウザの選択** | 設定でアプリ内 / Safari / Chrome を切替。**デフォルトはアプリ内ブラウザ** |
| F-05 | **既読管理** | 既読記事はグレーアウト。未読のみ表示するフィルタ |
| F-06 | **保存（あとで読む）** | スターを付けて別タブで一覧。**保存記事は自動削除の対象外** |
| F-07 | **プッシュ通知** | 新着記事を検知したら都度通知 |
| F-08 | **通知の団体別 ON/OFF** | 設定画面で団体ごとに通知の要否を切替 |
| F-09 | **ダークモード** | 端末のシステム設定に自動追従 |
| F-10 | **手動更新** | 一覧を引っ張って更新（Pull to Refresh） |
| F-11 | **更新記事の再浮上** | 公式サイト側で記事が書き換わった場合、検知して一覧の先頭に再表示し「更新」バッジを付与 |

### 4.2 第2弾以降（MVP には含めない）

| ID | 機能 | 見送り理由 |
|---|---|---|
| F-51 | 全文検索 | 記事が貯まってから実装すれば足りる |
| F-52 | カレンダー連携 | 記事本文からの日付抽出が必要で重い。精度を見ながら判断 |
| F-53 | 締切が近い順の表示（ハイブリッド型ホーム） | 同上。日付抽出の精度が前提 |
| F-54 | 作品・組の単位でのフォローと通知 | 記事から作品名を判定する仕組みが必要 |
| F-55 | 記事の共有（LINE 等） | 優先度低 |
| F-56 | ウィジェット | 優先度低 |

## 5. 非機能要件

| 項目 | 要件 |
|---|---|
| **対応 OS** | iOS 16 以降（iPhone のみ。iPad は考慮しない） |
| **収集間隔** | **1時間おき**（1日24回 × 5サイト = 120リクエスト／日） |
| **データ保持** | **団体ごとに最新100件**（計500件）。超過分は古い順に削除。ただし保存済み記事は削除しない（保存を解除した時点で削除対象に戻る） |
| **オフライン時** | 取得済みの記事は閲覧可能。更新時のみネットワークを要求 |
| **起動速度** | ローカル DB から即座に一覧表示。ネットワーク取得は裏で実行 |
| **通知の到達性** | ベストエフォート（FCM 経由。確実な到達は保証しない） |
| **相手サイトへの配慮** | User-Agent を明示。robots.txt を尊重。リクエスト間隔を空ける。**収集はサーバー側で1回のみ実行し、全ユーザーに配信**（利用者が増えてもアクセス数は増えない） |
| **運用コスト** | サーバー費用 **0円**（GitHub Actions 無料枠 + Firebase 無料枠） |

## 6. システム構成

### 6.1 全体像

```
┌─────────────────────────────────────────────┐
│  GitHub Actions（1時間おき / cron）           │
│  ┌───────────────────────────────────────┐  │
│  │ 収集バッチ（TypeScript / Node.js）      │  │
│  │  1. 5サイトを巡回（RSS または HTML）    │  │
│  │  2. 記事を抽出・正規化・カテゴリ判定    │  │
│  │  3. 前回との差分を検出                  │  │
│  │  4. articles.json を生成してコミット    │  │
│  │  5. 新着があれば FCM へ通知を送信        │  │
│  └───────────────────────────────────────┘  │
└──────────────┬──────────────────┬───────────┘
               │                  │
     articles.json          FCM（トピック配信）
     （GitHub Pages）              │
               │                  │
               ▼                  ▼
      ┌─────────────────────────────────┐
      │   CurtainCall（Flutter / iOS）   │
      │   ・起動時／Pull to Refresh／    │
      │     フォアグラウンド復帰時に     │
      │     JSON を取得                  │
      │   ・ローカル DB に保存           │
      │   ・既読／保存を端末内で管理     │
      └─────────────────────────────────┘
```

### 6.2 技術スタック

| 領域 | 採用技術 | 選定理由 |
|---|---|---|
| **アプリ** | **Flutter / Dart** | Dart は Java・TypeScript 経験者にとって読みやすくレビューしやすい。ホットリロードによる開発速度。将来の Android 展開が可能 |
| **収集バッチ** | **TypeScript / Node.js** | レビュー担当者の得意言語。スクレイピングのライブラリが充実 |
| **実行基盤** | **GitHub Actions** | 無料枠で1時間おきの定期実行が可能。コードとデータを同一リポジトリで管理できる |
| **データ配信** | **GitHub Pages（静的 JSON）** | サーバー不要・無料。CDN 経由で高速 |
| **プッシュ通知** | **Firebase Cloud Messaging** | 無料。**トピック購読方式**を採用し、デバイストークンの管理を不要にする |
| **ローカル DB** | **drift（SQLite）** | 型安全。既読・保存の管理に十分 |

### 6.3 通知の仕組み（トピック購読方式）

デバイストークンをサーバー側で管理しないため、**ユーザー管理もデータベースも不要**になる。

```
アプリ側： 設定で「宝塚 ON」→ FCM トピック "takarazuka" を購読
           設定で「東宝 OFF」→ トピック "toho" の購読を解除

バッチ側： 宝塚の新着を検知 → トピック "takarazuka" 宛に送信
           → 購読している全端末に届く
```

この方式により、F-08（団体別の通知 ON/OFF）が購読の切り替えだけで実現でき、個人情報を一切保持せずに済む。

**通知ペイロードには団体 ID（`companyId`）を含める。** アプリは通知タップで該当団体のタブを開く（S-01 §8 #20）。記事 URL は含めない（一覧を経由して開く）。

## 7. データモデル

### 7.1 記事（Article）

```typescript
{
  id:          string;   // URL のハッシュ値（安定した一意キー）
  companyId:   string;   // "takarazuka" | "shiki" | "horipro" | "toho" | "shinkansen"
  title:       string;   // 見出し
  url:         string;   // 公式サイトの記事 URL
  category:    string;   // "new_work" | "ticket" | "streaming" | "schedule" | "cast" | "person" | "other"
  publishedAt: string;   // ISO8601。サイト側の掲載日
  fetchedAt:   string;   // ISO8601。収集した日時
  thumbnail:   string?;  // サムネイル画像 URL（取得できた場合のみ）
  contentHash: string;   // 更新検知用のハッシュ値
  updatedAt:   string?;  // 更新を検知した日時（F-11 用）
}
```

**記事本文は保持しない。** 見出し・URL・メタ情報のみを扱うことで、権利面のリスクを回避する。

### 7.2 端末内で管理する状態

| テーブル | 内容 |
|---|---|
| `articles` | 取得した記事（団体ごと最新100件） |
| `read_states` | 既読フラグ（記事 ID と既読日時） |
| `saved_articles` | 保存した記事と保存日時（自動削除の対象外。保存日時は保存一覧の並び順に使う。S-02 §8 #6） |
| `settings` | 通知の団体別 ON/OFF（既定 ON）、ブラウザの選択（既定アプリ内）、未読フィルタの ON/OFF（既定 OFF。S-01 §8 #19） |

## 9. 制約とリスク

| # | リスク | 影響 | 対応方針 |
|---|---|---|---|
| R-1 | ~~公式サイトが RSS を提供していない可能性~~ | — | **解消（Phase 0）。** 2団体は RSS、3団体は静的 HTML で取得可能。動的生成サイトは無し |
| R-2 | **サイト改装で収集が壊れる** | 情報が更新されなくなる | 収集失敗を検知して通知する仕組みを入れる。サイトごとに処理を分離し、1サイトの故障が他に波及しない設計にする。対象は HTML 解析の3団体 |
| R-3 | **利用規約の複製禁止条項** | 身内共有の段階でリスクとなる | **robots.txt での制限は0件（Phase 0 で確認）。** ただし宝塚・四季は複製禁止の文言あり。自分専用のうちは私的使用の範囲。**TestFlight 配布時は緩和策を適用する**（調査レポート §6.2） |
| R-4 | **当日券・残席情報は取得困難** | 該当機能が実現しない | 公式の販売ページへのリンク提供に留める |
| R-5 | **カテゴリの自動判定精度** | 通知の絞り込みが不正確になる | ホリプロ・新感線・宝塚は**サイト側のカテゴリタグを流用できる**。四季・東宝はキーワード判定から始め、実データを見て調整する |
| R-6 | **無料 Apple ID ではプッシュ通知が使えず、アプリが7日で失効する** | F-07・F-08 が実現しない。実機での常用も不可 | Apple Developer Program（$99／年）への加入が前提条件。**フェーズ4 までは無料で進め、フェーズ5 の直前に加入する**（§10.1） |
| R-7 | **GitHub Actions の cron は実行時刻が遅延する** | 通知が数十分遅れる場合がある | 許容する（即時性は要件ではない） |
| R-8 | **東宝のドメイン分散** | 記事 URL が不整合になる | `toho.co.jp` / `tohostage.com` / `toho-navi.com` を吸収する URL 正規化処理を実装する |
| R-9 | **新感線の公式ドメインのフィードが空** | 記事が1件も取れない | 情報源は `blog.vi-shinkansen.co.jp` を参照する。公式ドメインのフィードは使わない |

## 10. 開発ロードマップ

「とにかく早く動くものを見たい」方針に従い、**通知とサーバーは後回しにして、まず画面に記事が並ぶ状態**を最短で作る。

| フェーズ | 内容 | 目安 | 成果物 |
|---|---|---|---|
| **0. 準備** | ~~5サイトの構造調査~~ **完了** ／ Xcode インストール ／ Flutter 環境構築 ／ コーディング規約の策定 | 1〜2日 | [調査レポート](./research/site-survey.md)、開発環境 |
| **1. 画面の骨格** | Flutter プロジェクト作成。**ダミーデータ**で団体タブ付きの一覧画面を実装。シミュレータで動作確認 | 2〜3日 | 動く画面 |
| **2. データ収集** | TypeScript で収集バッチを実装。ローカル実行で articles.json を生成。GitHub Actions で定期実行化 | 3〜4日 | 実データの JSON |
| **3. 結合** | アプリが実際の JSON を取得して表示。アプリ内ブラウザ連携。**この時点で当初の目的を達成** | 2日 | 実用可能なアプリ |
| **4. 使い勝手** | 既読管理・保存・ダークモード・設定画面 | 2〜3日 | 完成度の向上 |
| **5. 通知** | **Apple Developer Program 加入**／Firebase 設定／FCM 連携／**実機インストール** | 3〜4日 | 通知が届く |
| **6. 共有** | TestFlight 配布の準備 | 1〜2日 | 身内配布 |

**フェーズ3の完了（着手から2週間程度）で、当初の課題である「サイト横断の手間」は解消される。**

### 10.1 Apple Developer Program の加入時期

**フェーズ4 まで無料の Apple ID で進め、フェーズ5 の着手時に加入する**方針とした（2026-09-13 決定）。

| 判断根拠 | 内容 |
|---|---|
| フェーズ3 まではシミュレータで完結する | 実機もプッシュ通知も不要なため、無料アカウントで支障がない |
| 動くものを見てから判断できる | フェーズ3 完了時点で実データが流れるアプリが手元にあり、費用対効果を実感したうえで加入を決められる |
| 無料アカウントの7日失効が効くのはフェーズ5 以降 | 実機で常用し始める段階で初めて制約となる |

**留意点：** 加入時に本人確認で数日待たされる事例がある。**フェーズ4 の終盤に申し込んでおく**と、フェーズ5 で待ち時間が発生しない。
