### D-02 / D-03 への追随事項（まとめて reopen する）

今回の CI 障害調査（collect.yml が main で 10 回連続 failure）で判明した構造的な原因を含む。

- **D-02 §5.6 の補足表に 1 行追加**：`SOURCE_FACTORIES` が空の間（§10 Task I 完了〜D-03 §10 Task L 完了）は全団体が `not_implemented` となり §8 #25 の失敗判定でスケジュール実行が必ず失敗する。Task I では `collect.yml` の `schedule:` をコメントアウトした状態で導入し、`workflow_dispatch` だけで疎通を確認する。`schedule:` の有効化は Task L の差分に含める
- **D-02 §5.6「Pages の公開方式」の行に追記**：この手作業は §10 Task I の完了条件に含める。未実施のまま `published=true` の実行が来ると `deploy-pages` が Pages サイト未作成で失敗し、`data/articles.json` が push されても配信されない
- **D-02 §10 Task I の完了条件に 2 行追加**：`schedule:` はコメントアウトで入れる／リポジトリ設定の Pages ソースを「GitHub Actions」にして `gh api repos/<owner>/<repo>/pages` が 200 を返すことを確認する
- **D-03 §10 Task L の完了条件に追加**：マージ後に `workflow_dispatch` を 1 回実行して `sourceFailures` 0 件・`published=true`・`deploy-pages` 成功を確認する（次の `schedule` を待たない）。初回は `articles: []` のため §8 #27 により全団体 `fullCrawl` になり、団体あたり最大 100 件・最大 500 件が 1 コミットで push されることを織り込む
- **CLAUDE.md または D-02 §8 に一般則**：外部を定期実行するワークフロー（cron）は、その実行が成功しうる状態になるタスクと同じ差分で有効化する。先に有効化すると失敗が常態化して R-2（サイト改装の検知）のシグナルが埋もれる
