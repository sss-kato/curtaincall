### 第 1 段階で見つかった「設計書どおりに書くと実機で壊れる」欠陥 4 件

**いずれも D-04 の擬似コードを素直に実装すると踏むもので、レビュアーが SDK / ライブラリの実装を読んで実測で確認した。** 同種の再発を防ぐため D-04 への追随を後述する。

1. **タブ再タップの判定が常に true**（重大。4 人一致）— `CupertinoTabScaffold` は `tabBar.onTap` を呼ぶ**前**に `_controller.index` を更新する（`cupertino/tab_scaffold.dart`）。D-04 §5.8 の `index == currentIndex` を素直に書くと常に成立し、タブを切り替えるだけで先頭スクロール通知が飛ぶ（S-00/A-01 のスクロール位置保持が壊れる）。→ build 時点の index をクロージャに捕捉して比較する
2. **`shouldSyncOnResume` が実機で一度も true にならない**（高）— Flutter は `paused → resumed` を `[hidden, inactive, resumed]` に展開して配る（`services/binding.dart` の `_generateStateTransitions`）ため、`resumed` 時点の直前状態は常に `inactive`。フォアグラウンド復帰の取得（要件 §6.1 の 3 種のうち 1 つ）が丸ごと機能しない。→ 「直前の状態」ではなく「背景に入ったか」を持ち回る `resolveResumeSync` に変更
3. **`AsyncError` の写像が効かない**（高）— **Riverpod 3 は既定で自動リトライする**（`maxRetries = 10`、指数バックオフ）ため、Stream のエラーは約 50 秒間 `AsyncLoading(hasError: true)` として現れ、`AsyncData` / `AsyncError` しか見ない switch では `_ => null` に落ちる。記事があるのに全面ローディングが一覧を覆い、DB open 失敗も ST-14 にならない。→ 状態クラスではなく `hasValue` / `hasError` で写す `resolveHasArticles` に切り出し
4. **ログの増幅**（高）— provider の `build` 内の `ref.listen` は rebuild のたびに張り直されるため `fireImmediately` が毎回 `previous == null` で発火し、重複抑止のガードが素通りする。1 障害あたり 31 行（family 2 インスタンスなら 67 行）を実測。→ 何も watch しない専用 keepAlive provider `articleCountErrorLog` に listener を閉じ込め、判定を `shouldLogCountError` に切り出し
