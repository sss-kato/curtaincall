### 実装で効いた判断

- **`isChromeAvailable()` の例外捕捉**（4 人が一致）：D-05 §4.4 の例外行は `launchUrl` だけを対象としており設計違反ではなかったが、`canLaunchUrl` が `PlatformException` を投げると `chromeAvailableProvider` が `AsyncError` になり、§5.9 の判定（`.value == false`）が成立せず **E-13 が活性表示のままタップしても何も起きない**状態になる。`open()` / `closeInAppBrowser()` と契約をそろえて安全側（false = Chrome を選べない）に倒した
- **`settings` の watch に `.distinct()`**：D-04 §4.3 により `feed_etag` は同期のたびに upsert されるため、drift の select ストリームが無関係な書き込みでも再発火する。とくに `watchNotificationSettings()` は毎回新しい `Map` を返すため、同期のたびに設定画面の通知トグル群が再構築されていた
- **CI に `Info.plist` の検査を追加**：D-05 §8 が「T-H2 の完了条件で plist を検査する」と定めているのに一度きりの人手確認に閉じていた。この 2 行が失われても `analyze` / `test` は通り、`isChromeAvailable()` が常に false になるだけで失敗として観測されない

### 残っている「低」の指摘（対応は任意）

- ポートの呼称が「外部境界」（本タスクの 3 ポート）と「読み書き口」（`SettingsRepository`・`ArticlesFeed` など D-04 由来）で併存している。Repository IF と外部境界ポートを意図的に呼び分けているなら現状で正しい
- Chrome のスキーム文字列が Dart 定数・`Info.plist`・ワークフローの 3 箇所にあり、**CI が保証するのは後 2 者の一致だけ**。Dart 定数を変えても CI は無反応（参照先をコメントで固定する対応にとどめた）
- `_ThrowingSettingsRepository` が 9 メソッドを手書きしており、IF が増えるたびに無関係なテストファイルが編集対象になる
- `one_member_abstracts` の ignore が lib 内 4 箇所。**外部境界のポートは ISP により 1 メソッドになるのが正常**なので `analysis_options.yaml` で切る案
