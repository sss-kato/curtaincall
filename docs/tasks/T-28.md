### 設計書への追随事項（D-05。**まとめて reopen する**）

§5.11 に関する 9 件。うち 7 件は「設計書どおりに書くと Flutter SDK の内部仕様に抵触する / 位置がずれる」種別。

- **§5.11「構成（2 形態）」：アンカー形では `leadingSlivers` を `slivers` に入れない。** 設計書は両形態で `[...leadingSlivers, ...]` と書き「`CupertinoSliverRefreshControl` は発火しない。実害は無い」とするが、実際は `assert(constraints.growthDirection == GrowthDirection.forward)` を持つため **debug ビルドで落ちる**。末尾の「並び（上から）」と「どちらの形態でも `leadingSlivers` が `slivers` の先頭」も同時に改訂する
- **§5.11「アンカーの更新」手順 3：`correctPixels(-anchorDy)` では足りない。** アンカー形へ遷移する場合しか成立しない。新レイアウトが標準形のときは `correctPixels(H - anchorDy)` が必要。H の優先順位を明記する：(1) 旧レイアウトも標準形なら旧先頭セルの実測 `position.pixels - position.minScrollExtent + dy`（**`minScrollExtent` の正規化を省かない**）／(2) 旧アンカー形・実測不可ならヘッダ Sliver の `constraints.precedingScrollExtent + geometry.scrollExtent`／(3) どちらも取れなければ補正しない。アンカー形へ遷移する場合の H は 0
- **§5.11：`didUpdateWidget` の処理順を「アンカーの更新 → セルの `GlobalKey` の刈り取り」と明記する。** 逆順だと実測に使う旧セルのキーが先に捨てられ、経路 1 が常に失敗する
- **§5.11：`position` に触れる前のガードを明記する。** `hasClients` かつ `position.hasContentDimensions`。`State.didUpdateWidget` は `Scrollable` が新 controller を受け取るより**前**に走るため、差し替え直後は `hasClients == false`
- **§5.11：`ScrollController` の差し替えでは `ScrollPosition` が再利用される。** `Scrollable._shouldUpdatePosition` は controller 同士の差し替えでは false を返し `absorb` すら経由しない。「新しい controller なので `pixels` は 0 から」と仮定できない
- **§5.11：`_ExtentCompensatingSliver` には `GlobalKey` が必須。** 形態の切替で Element が作り直されると「前回のレイアウトの extent」が 0 に戻り、帯が「出現した」と誤認されて二重補正になる
- **§5.11「未アタッチ時の `scrollToTop()`」：`detach(_AnchoredListTarget state)` を受け `identical(_target, state)` のときだけクリアする。** ページ切替では新 State の `attach` が旧 State の `detach` より先に走る
- **§7：`AnchoredListView` をテストしない方針は維持**したうえで、「依存する SDK 内部の前提と確認した Flutter のバージョンをファイル冒頭の library doc に列挙して残す」を運用として書き足す
- §10 T-M の目視項目に、目視で確認できるもの（アンカー形での引っ張り更新の不発、帯の出現・消失、ページ切替直後の差し込み）を対応づける
