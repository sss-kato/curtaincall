## 内容

`GitArticlesPublisher.publish()` は手順 3-3 で `git commit` してから手順 3-4 で `git push` する。push が失敗すると手順 3-6 の復元 `git checkout origin/main -- data/articles.json` が走るが、**これは作業ツリーと index を戻すだけで、手順 3-3 で作ったローカルコミットは残る**。

同じ作業ツリーで次回実行すると、`git add` 後の `git diff --cached --quiet` が 0（HEAD と一致）を返すため、新着があるのに `no_changes` を返して**成功扱いで終わる**。配信が止まったまま障害が隠れる（要件 R-2 の検知を損なう）。

GitHub Actions は毎回クリーンチェックアウトなので現状は自己回復するが、ローカル実行・セルフホストランナーでは成立しない。

**publish のホットフィックス（`isExecFileError` の `null` 未対応の修正）によって commit / push が本番で初めて到達可能になった**ため、これまで顕在化していなかっただけである点に注意。

## 完了条件

### 取り下げの理由

**1. 対象の障害が現行構成では到達不能（spec 高）**

- `.github/workflows/` の全ジョブが `runs-on: ubuntu-latest`。**セルフホストランナーは存在しない**
  （本タスクの前提「ローカル実行・セルフホストランナーでは成立しない」は事実と違っていた）
- ローカル実行は §4.9 が `CURTAINCALL_DRY_RUN=1` を必須の運用規約とし、`main.ts` が
  `NoopArticlesPublisher` を注入するため **`GitArticlesPublisher.publish()` 自体が呼ばれない**
- D-02 §6（1071 行）はこの障害シナリオを行として列挙済みで、対処は `git reset --hard origin/main`、
  分類は「運用」。設計は問題を見落としたのではなく、認識したうえでコードではなく運用で解くと決めている
- 要件 R-2 との関係でも必要性は立たない。push 失敗は `PublishFailedError` → 終了コード 1 →
  §8 #25 の失敗通知で必ず開発者に届く

**2. 承認済み設計の決定を覆していた（spec 重大）**

D-02 §8 #10 は決定列に「push 失敗時のローカルコミットの巻き戻し（`git reset --soft HEAD^`）も
**実装しない**」と書き、検討した代案列に「push 失敗時に `reset --soft HEAD^` で巻き戻す」を挙げ、
理由列で「巻き戻しは runner では不要で、必要になるのはローカルで push まで行った場合だけ。
その場合は DRY_RUN で push 自体を起こさない方が単純で、**`reset` の失敗という分岐も増えない**」と
却下している。実装は却下された代案をそのまま採用していた。

**3. 実装が新しい障害を生んでいた（security・architecture・typescript-expert・adversarial 中）**

- `preCommitHead` を commit の**前**に採取するため、commit 失敗と push 失敗を区別できない。
  判定は「`HEAD^` == `preCommitHead`」だけで「現在の HEAD が自分のコミットである」ことを確認しておらず、
  **commit 失敗中に他プロセスがコミットを積むと、そのコミットを `reset --soft` で HEAD から外す**
- push をリモートが受理した直後にクライアントが切断すると、origin には C1 があるのにローカルだけ
  C0 に戻る。修正前は次回 `no_changes` で自然に収束したが、**修正後は恒久的な non-fast-forward で
  失敗し続ける**（`fetch`/`rebase` の経路が無い）
- commit 失敗時に「HEAD advanced unexpectedly」という事実と異なる警告が出て、障害調査を誤誘導する
- unborn HEAD では `rev-parse HEAD` が失敗し、本来成功する publish が落ちる
- reset を見送った場合、次回以降の実行は `no_changes` で静かに成功扱いに戻り、本タスクが塞いだ
  隠蔽がそのまま再発する（警告はスキップした回にしか出ない）

**4. 完了条件が検証できていなかった（adversarial 中）**

核心の回帰テストは、スタブが `git add` のたびに無条件で「差分あり」にしていたため、
**障害そのもの（残ったコミットと add 内容が同一で `diff --cached --quiet` が 0 を返す）が
再現されていなかった**。ミューテーションで実証：`revertOwnCommit` の呼び出しを削除しても、
テストの主眼である `resolves.toBe("published")` はそのまま通る。

### この判断で確認できたこと

D-02 §8 #10 が `reset --soft HEAD^` を却下した理由（「`reset` の失敗という分岐も増えない」）は、
実装してみて具体的に裏付けられた。分岐は誤警告・他人のコミットの喪失・恒久的な
non-fast-forward の 3 つを生んだ。**設計判断が正しかったことがレビューで確認された形。**
