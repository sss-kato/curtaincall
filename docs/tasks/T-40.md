## 内容

対応外 `schemaVersion` を検知している間は起動時・復帰時の取得を抑止するが、現在の設計では `SyncCoordinator._start` が `SyncStarted` を流した**後**に `SyncArticlesUseCase` の中で抑止を判定している。そのため `inProgress` が true になり、S-00/E-21（更新中インジケータ）が出てしまう。抑止判定は DB 読みを伴い、`launch` では DB の open と migration を含むため 1 フレームを超えうる。

判定を `SyncSuppressionPolicy` として切り出し、`SyncCoordinator` が `execute` を呼ぶ前に評価する。抑止時は **`SyncStarted` を流さず** `SyncCompleted(trigger, SyncFailed(unsupportedSchema, suppressed: true))` だけを流す。これで「取得そのものを行わなかったときは E-21 も E-25 も出さない」（S-00 §8 #31・S-01 §8 #23）を構造で担保する。

あわせて `_start` の手順 3 (b) で `_disposed` と `isCancelled()` を再確認する。抑止判定の完了前に全体タイムアウトすると、対応する `SyncCompleted` の無い `SyncStarted` が後から流れて `inProgress` が true のまま固まるため。

### 残っている「低」の指摘（対応は任意）

- `SyncSuppressionPolicy` が `unsupportedSchemaVersion()` の 1 メソッドしか使わないのに 6 メソッドの `ArticleSyncRepository` に依存（ISP）。D-04 §5.2.1 が承認済みの形のため範囲外
- `_realStack`（`sync_coordinator_test.dart`）と `_buildEnv`（`sync_articles_use_case_test.dart`）に実物結線が二重にある。maintainability は「目的が異なるため統合は求めない」と判断

### 対応しなかった指摘

- 壊れた `feed_unsupported_schema` の値による `FormatException`（`int.tryParse` 化）。`DriftArticleRepository` の契約変更で D-04 に記述が無く範囲外。security 自身も「現状のままで可」とし、`on Object` 化により実害が消えたとして第 3 周で指摘を取り下げ
- 抑止判定失敗時の logger 出力。`SyncCoordinator` は Logger を持たない設計（D-04 §5.3）のため D-04 の改訂が前提

### 残課題（コードから削り、ここに記録したもの）

- **抑止判定の失敗が無症状になりうる。** 判定が失敗すると「抑止しない」に倒れるが、判定ロジック自身の欠陥（`TypeError` 等）では続く `execute` が正常成功するため、抑止が恒久的に効かない状態がログにも結果にも現れない。`SyncCoordinator` が Logger を持たない設計（D-04 §5.3）の帰結。診断を残すには D-04 の改訂が要る
- 抑止理由が 2 つ目になると `Future<bool>` の契約・`SyncCoordinator` の固定リテラル・DI・全テストに波及する。`Future<SyncResult?>`（null = 抑止しない）への改訂を検討
