## 内容

T-28 で実装した `AnchoredListView` は、位置保持のアンカーを決める走査規則を `_AnchoredListViewState` の中に持っている。D-05 §5.11.4 はこれを純粋関数 `resolveAnchorId` として切り出し、テーブル駆動テストで担保することを定めた（§8 #33）。実装済みコードからの切り出しだけを行う片付けタスク。

走査規則が State 側に重複して残らないこと（切り出したのに両方に実装がある状態にしないこと）が要点。

### 検証の要点

- **振る舞い等価**：adversarial-reviewer が **5 つの変異体**（「直後の 1 件だけを見る」「`index < 0` のガードを外す」「早期 return を外す」「前方走査にする」「`newIds.first` に倒す」）を作って 7 ケース表に通し、**すべて kill** されることを確認（worktree は書き換えず scratchpad 上で実施）。切り出し前の実装との 1 ケースずつの突合も実施
- `indexWhere` → `indexOf` は**どちらも最初の一致**を返すため `oldIds` に重複があっても差が出ない。新設した `index < 0 → null` は**旧実装では到達不能だった経路の明示化**（旧 `topId` は必ず `oldItems` 由来）で、旧の潜在挙動（先頭から走査）より安全側
- D-05 §6 の `resolveAnchorId` 関連 5 行がすべて切り出し後も同じ経路で成立することを確認
- リネーム（`topId`→`visibleId`・`topDy`→`anchorDy`）と名前付き引数化（`{required oldItems, required newItems}`）は司令塔が差分を精査し、取り違えが無いことを確認
