## 内容

D-02（approved、2026-09-25）§8.1 の実装追随 **(d)**。**秘密情報がログに残る経路を塞ぐ。**

現行の `main.ts` 手順 4 は通知ゲートウェイの生成失敗を `logger.error(..., { error: formatError(e) })` で出しており、`JSON.parse` の `SyntaxError` 経由で**サービスアカウント JSON の断片が Actions のログに残りうる**。あわせて `FirebaseNotificationGateway` が生の JSON 文字列を受け取って `send()` で遅延初期化する形だと、`formatError` の `cause` 再帰連結（§4.7）で同じ漏洩が送信時に起きる。

D-02 §5.4・§5.5 手順 4a・5 が次の形に確定している。

- **`main.ts` 手順 4a が `JSON.parse` を 1 回だけ行う。** 結果を `unknown` として受け、`typeof v === "object" && v !== null && !Array.isArray(v)` の型ガードで `Readonly<Record<string, unknown>>` へ絞ってから渡す（`any` 禁止）
- **`FirebaseNotificationGateway` のコンストラクタは `constructor(serviceAccount: Readonly<Record<string, unknown>>, logger: Logger)`。** 環境変数も生の JSON 文字列も受け取らない。第 1 引数を `firebase-admin` の `ServiceAccount` に**しない**のは、そうすると `main.ts` がその型を import することになり §8 #17（firebase-admin を `infrastructure/fcm` に閉じる）と矛盾するため。**`main.ts` に `firebase-admin` の型が 1 つも現れないこと**
- **初期化はコンストラクタで行う**（`initializeApp({ credential: cert(serviceAccount) })` を `getApps().length === 0` のときだけ）。`send()` へ遅延させない
- パース失敗は手順 4a が固定文言で、初期化失敗は手順 5 が固定文言 `failed to initialize FCM with FIREBASE_SERVICE_ACCOUNT` で捕まえ、終了コード 1
- **`NotificationSendError.cause` に入れてよいのは firebase-admin が送信時に投げた例外だけ。** サービスアカウント JSON を入力に持つ例外（`JSON.parse` の `SyntaxError`・`cert()` / `initializeApp` の失敗）は `cause` に入れない
