## 内容

D-02（approved、2026-09-25）§8.1 の実装追随 **(d)**。**秘密情報がログに残る経路を塞ぐ。**

現行の `main.ts` 手順 4 は通知ゲートウェイの生成失敗を `logger.error(..., { error: formatError(e) })` で出しており、`JSON.parse` の `SyntaxError` 経由で**サービスアカウント JSON の断片が Actions のログに残りうる**。あわせて `FirebaseNotificationGateway` が生の JSON 文字列を受け取って `send()` で遅延初期化する形だと、`formatError` の `cause` 再帰連結（§4.7）で同じ漏洩が送信時に起きる。

D-02 §5.4・§5.5 手順 4a・5 が次の形に確定している。

- **`main.ts` 手順 4a が `JSON.parse` を 1 回だけ行う。** 結果を `unknown` として受け、`typeof v === "object" && v !== null && !Array.isArray(v)` の型ガードで `Readonly<Record<string, unknown>>` へ絞ってから渡す（`any` 禁止）
- **`FirebaseNotificationGateway` のコンストラクタは `constructor(serviceAccount: Readonly<Record<string, unknown>>, logger: Logger)`。** 環境変数も生の JSON 文字列も受け取らない。第 1 引数を `firebase-admin` の `ServiceAccount` に**しない**のは、そうすると `main.ts` がその型を import することになり §8 #17（firebase-admin を `infrastructure/fcm` に閉じる）と矛盾するため。**`main.ts` に `firebase-admin` の型が 1 つも現れないこと**
- **初期化はコンストラクタで行う**（`initializeApp({ credential: cert(serviceAccount) })` を `getApps().length === 0` のときだけ）。`send()` へ遅延させない
- パース失敗は手順 4a が固定文言で、初期化失敗は手順 5 が固定文言 `failed to initialize FCM with FIREBASE_SERVICE_ACCOUNT` で捕まえ、終了コード 1
- **`NotificationSendError.cause` に入れてよいのは firebase-admin が送信時に投げた例外だけ。** サービスアカウント JSON を入力に持つ例外（`JSON.parse` の `SyntaxError`・`cert()` / `initializeApp` の失敗）は `cause` に入れない

### 検証の要点

**中核（壊れた secret で固定文言だけが出ること）は自動テストを持たない**（D-02 §7 と §8 #56 が承知のうえで選んだ carve-out の外側）。そのため adversarial が**実バイナリを起動した手動検証**で担保した。**この経路を次に触る担当者は同じ検証を再実行すること。**

**手順**：`npm run build` したうえで `dist/main.js` を子プロセスで起動し、`FIREBASE_SERVICE_ACCOUNT` に下記 16 通りを与えて `CURTAINCALL_LOG_LEVEL=debug` で実行。stdout + stderr 全文を**秘密のマーカー**（鍵本体の先頭 20 文字・`BEGIN PRIVATE KEY`・`client_email`・`project_id`）で走査する。

**入力 16 通り**：切断 JSON ／ 末尾ゴミ ／ BOM 付き ／ 配列 ／ 文字列リテラル ／ 数値 ／ `null` ／ `{}` ／ 必須キー欠落 ／ 空 `private_key` ／ 数値 `private_key` ／ snake・camel の壊れた PEM ／ 改行未エスケープ PEM ／ 余分キー ／ 40KB 鍵 ／ 制御文字・引用符・改行入り ／ `__proto__` 汚染 ／ 実 RSA 鍵での成功経路

**実測結果**：全件で **exit=1、出力は固定文言のみの 1〜2 行、秘密の断片 0 件**。ログインジェクション（偽 `key=value` の挿入）も再現せず。成功経路の出力は `debug fcm gateway initialized` のみ。

そのほか：
- **`NO_APP` の誤帰属の解消**を、名前付きアプリを実際に登録した状態から実鍵で構築して実測
- **連結子を変えるミューテーション（M3）が検出されるようになった**ことを確認（第 1 段階第 2 周までは 486 テスト全通過だった）
- `error` → `warn` への格下げで検知が弱まらないこと（既定レベルで stderr に出て exit=1、`collect.yml` に `continue-on-error` が無いのでジョブは赤）を確認

### 開発者に確認してほしいこと

**1. 自動テストの carve-out（承認事項）**

T-45 の中核と `formatError` の `cause` 再帰には自動テストが無い。maintainability の評価は「**保守性の観点では「高」には当たらない**（承認済み D-02 §7 と §8 #56 が明示的に選んだ carve-out の外側だから）。ただし**リスクの形が非対称かつ不可逆**である」というもの。

- 退行しても品質ゲートは緑のまま（静かな失敗）
- 退行の結果が**公開リポジトリの Actions ログへの秘密鍵断片の流出**で、検知後もログ保持期間と鍵のローテーションが必要になり巻き戻せない
- 防壁が 2 層あるが、**両方とも無検証の層に属する**

対処するなら **D-02 §7.3 の carve-out に `FirebaseNotificationGateway`（外部境界かつ秘密情報の唯一の入力点）と `domain/logger.ts` の `formatError`（純粋関数）を追加**し、CLAUDE.md「テスト方針」の対応行も更新する。**`/design-doc reopen D-02` → `/design-review` の経路が要る。**
