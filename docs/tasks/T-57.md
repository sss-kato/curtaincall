## 内容

`docs/tasks/FOLLOWUPS.md` §4 の **4-1** を片付ける。`build_runner` の生成物（`*.g.dart`）はコミットする運用（D-04 §3.2「生成物」）なので、**ソースと生成物の食い違いは人が再生成して比較しない限り見つからない**。実際に T-39 で 1 回すり抜けた。

- **`app/lib/app/minute_clock.g.dart` の source hash が現在のソースと一致しない**（T-28 の `build_runner` 再実行漏れ。T-40 の報告で検出）。`dart run build_runner build --delete-conflicting-outputs` を実行して当該ファイルの差分だけを取り込む
- **`app/lib/core/database/app_database.g.dart` の相違は formatter のスタイル差で内容は同一のため対象外**（FOLLOWUPS §4 4-1）。再生成すると 172 行の差分が出るが、これは drift_dev が内蔵する dart_style が SDK より古いための整形差（関数型 typedef の折り返しのみ。意味変更なし）で、取り込むと `dart format --output=none --set-exit-if-changed lib test` が落ちる（FOLLOWUPS §6「drift を触るタスク」）。**このファイルは差分を捨てる**

### 本タスクで扱わないこと

**FOLLOWUPS 4-2（CI への生成物の鮮度検査の追加）は本タスクの範囲外。** `.github/workflows/app-ci.yml` で `build_runner` を走らせる案だが、**D-04 §3.2 が「`*.g.dart` はコミットする（`build_runner` を CI で走らせない。§4.8）」と明記している**ため、承認済みの設計書の決定を実装タスクで覆すことになる。`/design-doc reopen D-04` → §3.2・§4.8 の改訂 → `/design-review D-04` → `/design-doc approve D-04` が前提。加えて 4-2 自身が「drift_dev の更新とセットで検討する」と留保しており、上記の `app_database.g.dart` の整形差がある限り素直な `git diff --exit-code app/lib` は赤になる。4-2 は FOLLOWUPS に残したままにする。
